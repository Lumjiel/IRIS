# Research: AI/LLM 简历项目功能完备性的实证证据

## Summary
面试官对 Agent 简历项目验收的核心不是「功能多不多」,而是「你能不能证明它是工程系统而不是 Demo」:真实问题叙事、可验证的评测、可回放的 Trace、工具失败处理是最被反复核验的四件事。**最值得补齐的功能排序是:①上线可试的 Live Demo → ②评估体系 → ③可观测性/Trace → ④工具稳定性(超时/重试/幂等/HITL)→ ⑤记忆系统设计决策 → ⑥上下文工程与成本控制**。最强反例来自真实面试:候选人堆满 LangGraph 多 Agent + GraphRAG + 微调 + Neo4j,被一句"豆包直接能解决,为什么还要做?"击穿。

---

## 1. 招聘者/面试官到底验收哪些功能点(一手/准一手证据)

1. **F5(人力资源机构,80,000+ 候选人库)的 AI Agent Developer 筛选清单**:生产级定义 = 能讲清 ①state schema 设计及原因 ②memory 架构权衡(短期/工作记忆/长期检索) ③评测方法论 ④一次真实生产事故的根因与修复。8 项硬能力:求解器编排(LangGraph 等)、**工具/函数调用设计(含 malformed 输出处理、retry/fallback——"多数 agent 故障源头")**、跨轮次 state 管理、memory 架构、**评测与可观测性(LangSmith/Weave/RAGAS)**、结构化输出解析、受约束的 Prompt 工程、prompt injection 意识。红旗:只讲用哪个模型、讲不出生产事故 = prototype 级别。技术评估要考察:schema 设计是否显式可检视、工具失败行为、**是否写过 eval/test**、代码结构、**是否加了观测(logging/tracing)**。可信度:高(结构化方法论)。[F5 Hiring Solutions](https://f5hiringsolutions.com/blog/what-to-look-for-ai-agent-developer)

2. **2026 年 Agent 专项招聘的 6 大技能区 + 5 大组合信号**:Tool use、Orchestration、HITL 设计、**Observability(结构化 trace/span)**、MCP 集成、**Eval-driven iteration**。求职信号分级:agent trace with visible reasoning(公开可共享的 trace,不截图要链接)= **High**;eval harness + 成功标准 + 结果表 = **High**;tool schema 设计文档 = **High**;HITL 决策日志 = Medium;MCP server = Medium。并明确写:"简历上写 'built multi-agent pipeline using LangGraph' 和完成教程的人无法区分""没有 evals 常常足以丢 offer"。可信度:中高(招聘平台方法论,带自推销成分)。[aitechconnect](https://aitechconnect.in/tips/agentic-ai-role-portfolio-interview-2026)

3. **真实 80 分钟面试完整复盘(面试官本人撰写,2026)**:候选人简历正是「LangGraph 多 Agent 健康助手 + Agent 长期记忆引擎」——与你的项目类型几乎一致。面试官全部问题实录:
   - 灵魂一击:"如果是我的话,豆包直接就能解决,为什么要做这个?"(项目存在理由 = 真实问题 × 现成方案不足)
   - 连续"为什么 X 不用 Y":为什么 Milvus/Chroma?多 Agent 是否通信(固定 Router 分发 = Workflow **不是** Multi-Agent)?90.6% 意图准确率怎么算的(测试集构成/分布/边界用例)?为什么 Redis(面试官:"只为 TTL 用 Redis 是不懂 Redis,记忆数据是最宝贵的资产,不能像缓存一样过期删除")?为什么微调 Qwen3-8B?上下文怎么做(简历写"context management"一行 = 空话)?
   - 记忆系统灵魂问题:"用户说今天我吃辣——短时偏好 vs 长期偏好怎么分?"(候选人答不出)
   - 成本控制:"减少调用次数"= 结果不是方法,必须讲 prefix caching / 模型分层 / 上下文裁剪
   - 结论:"**简历上写的每一个技术点都是你应答不透彻的洞**""一个项目做深 >> 五个项目做浅""项目要能上线、最好让面试官亲手试""如果做到了 replay(可回放调试),那真的很大加分"。可信度:高(一手面试记录,与目标项目同构)。[Joye Huang 1h19m 模拟面试复盘](https://www.joyehuang.me/blog/20260512---agentmockinterview/post)(英文版 [EN](https://www.joyehuang.me/en/blog/20260512---agentmockinterview/post))

4. **第二场 46 分钟面试复盘**:实验了 Agent 评估(#33 候选人"没了解过" = 当次扣分点)、RAG 痛点、prefix-cache 工程细节、multi-agent 优势(并发 + 模型组合,而非"能完成复杂任务"……且 multi-agent 总 token 约 15× 单 agent,Anthropic 官方数据)。还暴露"简历措辞与实际实现不符"是地雷(候选人在面试中被抓到)。可信度:高。[Joye Huang 46 分钟面试复盘](https://www.joyehuang.me/en/blog/20260528---agentmockinterviewreview/post)

5. **中文一线追问框架(JavaGuide)**:面试官追问核验三件事——项目是不是真的、有没有技术决策能力、对系统边界的认知。有效回答结构 = **约束 + 选择 + 代价 + 证据**;常见评价陷阱:"Multi-Agent 提升了效果"(没交代拆分原因与代价)。给出完整项目复盘表(业务问题/成功标准/关键约束/质量证据/失败案例/证据位置)和 15 条自测(如"哪些决策由模型做、哪些必须由代码做""写操作如何授权/幂等/核验""Trace 怎么逐节点解释")。可信度:高(国内知名站、内容具体可核)。[JavaGuide](https://javaguide.cn/ai/interview-questions/agent-project-interview-guide.html)

6. **行业量化差异(LangChain 官方)**:89% 的组织已实现 observability,但只有 52% 跑离线 eval、37% 跑在线 eval——"看得到 agent 在做什么"已成标配,而"判断它做得好不好"是稀缺差异点,这正是简历项目拉开差距的位置。可信度:高(官方调研)。[LangChain: Evaluating AI Agents](https://www.langchain.com/resources/agent-evals)

7. **配套佐证**:招聘者说"会调 OpenAI API 的 chatbot 不算工程,要看到 end-to-end pipeline"(Umer Sufyan,招聘者周更流水账,[LinkedIn](https://www.linkedin.com/posts/usufyan_your-chatbot-project-wont-get-you-hired-activity-7412787312008265739-JzbE));"面试定生死的问题变成 'Walk me through an eval you designed'"(Sagar Rathkanthiwar,[LinkedIn](https://www.linkedin.com/posts/sagar-rathkanthiwar-b5537110_ai-machinelearning-careergrowth-activity-7486419945980067840-9jcg));"demo 的关键信号是 demo 失效时怎么办"([Provn](https://provn.co/blog/2026/06/agentic-engineer-hiring-requirements));胜任力=判断与权衡,tool 知识只是地板([TryCrucible](https://trycrucible.io/blog/what-ai-hiring-managers-actually-look-for))。可信度:中。

## 2. "某功能确实加分"的具体案例

1. **Live 实机 Demo(带 LangGraph)直接转化面试**:候选人拿到技术面通知后,用 FastAPI + Uvicorn + **LangGraph** + Claude 为对方公司定制了一版实机 Demo(匹配公司品牌视觉、可在线访问),用它边学边做并证明自己能交付;文章标题即"Got the Technical Interview — Proved I Could Do It"。印证了"让面试官亲手试的项目远比简历描述加分"(与第 1.3 条面试官原话互相印证)。可信度:中(一手自述,但目标页大量垃圾评论、正文细节未能完整核实)。[matthewraynor.com](https://matthewraynor.com/blog/got-the-technical-interview-so-i-built-a-live-demo/)

2. **面试官在实录中认证的具体加分点**(高可信,见 1.3/1.4):
   - "如果项目做了 **replay(可回放调试)**,那真的是很大加分"——即可观测性/Trace 回放被面试官点名加分;
   - 90.6% 准确率回答里"无法识别时 fallback 到 Text2SQL"被记为 bonus point(失败兜底 = 加分);
   - **多模型分层**(意图识别用小模型、汇总用大模型)被面试官明确称赞"我很认可,这说明你从生产角度思考";
   - 部署上线、面试官可试用 = "远比纯简历描述加分"。

3. **记忆架构直接带来面试机会**:候选人在黑客松与 Mastra 赞助商深聊 **RAG 记忆架构**,两天后拿到 OpenAI 面试 referral(自述)。可信度:低(LinkedIn 一手自述,无法核实面试是否成行)。[Gabriel Fagundes Teixeira](https://www.linkedin.com/posts/gabrielft-me_rags-summerintern-internship-activity-7430627356618432513-0mDQ)

4. **组合证据(中/低可信度,自述类)**:5 个生产质量项目(每个含工程证据)支撑 24 岁拿 senior + 六位数薪酬,自述"面试从审讯变成讨论"——强调生产级证据链而非数量([Zen van Riel](https://zenvanriel.com/ai-engineer-blog/100k-ai-engineering-portfolio-projects/));AI 求职 agent 项目带来 11 个一面([Jean Kurt](https://www.linkedin.com/posts/jeankurt_github-kurt-chanai-job-scraper-activity-7480806804764131328-MlmJ));MBA 候选人靠 AI 原型在投递前拿到面试([Conversations on Careers](https://conversationsoncareers.com/2026/06/ai-ready-tejash-bagris-ai-prototype-landed-him-an-interview/))。

5. **特定"加分点"的最强实证是聚合意见**:多个独立招聘方来源(1.1/1.2/1.6)的一致结论——trace、eval、tool schema 是简历项目最高信号功能,而非 model/框架选择。可信度:中高。

6. **需警惕的"案例"**:自称用 LangChain 项目拿到 Stripe $412k 的"war story"、以及同站同模板的 Google $400k 案例([johal.in](https://johal.in/war-story-got-400k-offer-stripe-building-project))——页面 503 无法抓取、两篇故事结构雷同、纯自述无任何可核验细节,判断为 SEO 营销内容。可信度:低,不建议作为决策依据。

## 3. 反例:加什么功能反而被扣分(真实案例)

1. **最典型(高可信,真实面试实录)**:上面 1.3 那位 LangGraph 多 Agent 候选人的项目几乎焊死了所有"看起来高级"的功能——Router + 多 Agent 分层、GraphRAG、三层记忆、ChromaDB + Neo4j 混合图向量检索、艾宾浩斯遗忘曲线、Qwen3-8B 微调。面试官的评价:**"先决定要用 LangGraph / Multi-Agent / GraphRAG / 微调,再找一个场景把这些技术塞进去""堆砌技术是 2026 年 Agent 求职者最普遍的问题,任何有经验的面试官 5 分钟内就能看穿""只要写了我就问,答不出就是减分"**。过度设计照样被扣分,因为复杂度没有对应的问题收益。可信度:高。[Joye Huang 复盘](https://www.joyehuang.me/blog/20260512---agentmockinterview/post)

2. **面试官吐槽(中可信度,招聘者一手帖)**:候选人"个人简历项目的基础设施比我们整个创业公司生产环境还多""一个用向量数据库加持的 GenAI 任务优先级引擎"——招聘者称之为 **"Resume Driven Development" 到了顶点**,讽刺味十足地宣告"候选人不再为解决问题而构建"。可信度:中。[Gunjan Sharma, LinkedIn](https://www.linkedin.com/posts/gunjan1sharma_i-interviewed-a-candidate-today-whose-personal-activity-7399728694371672067-QgOV)

3. **框架熟、原理弱(中可信度,面试官帖)**:候选人"能讲 LangGraph workflow 讲 10 分钟,但说不清 Transformer 基础""RAG 很会搭,但不会评估 RAG"——被系统性地记为减分信号。可信度:中。[Bharath Reddy, LinkedIn](https://www.linkedin.com/posts/bharath-reddy-35a405195_ive-been-interviewing-ai-engineer-candidates-activity-7493614832680747009-gCDC)

4. **项目数量堆砌(中可信度)**:招聘者自述拒绝了一位简历上有 36 个 ML 项目、却讲不清监督/无监督区别的候选人。可信度:中。[Shyam Kashyap, LinkedIn](https://www.linkedin.com/posts/hvskashyap_hiring-techrecruitment-leadership-activity-7425739084737810432-eGd0)

5. **"功能堆满但无评估无观测"被明确判为低含金量**(中文圈,可信度:中):文章直接列出三类 2026 年已难加分的项目——聊天 UI + API 透传、照文档跑通框架讲不清为什么、**有 RAG 有工具有 memory 但没有指标、没有 trace、无法回放**(面试官判断:"你无法证明效果,也无法迭代")。[HTMLPAGE](https://htmlpage.cn/topics/ai/ai-agent-project-credibility-guide)

6. **真实面试口头反馈(中可信度)**:候选人自我感觉良好地讲完 MCP + RAG + Function Calling,面试官当场一句"**你这个太 toy 了**"——"玩具=只能跑通 Demo,离工程化差得远",MCP/RAG/Function Calling 被明确定性为起点而非卖点。[CSDN](https://blog.csdn.net/m0_59235945/article/details/162238833)

7. **共性反模式归纳**(多来源一致):通用动词 + 热门框架名、无测量无范围无信号(Rejectless,[链接](https://www.rejectless.app/guides/genai-resume-bullets));简历靠 AI 生成导致"同质化流行病"(Business Insider,[链接](https://www.businessinsider.com/how-to-avoid-sounding-job-application-written-ai-2025-7));"完美项目"没有"你舍弃了什么"的可信证据(LinkedIn 招聘者复盘,[链接](https://www.linkedin.com/posts/ahsankhalid-aiengineer_aiengineering-llm-careeradvice-activity-7485017024830693377-ZXbg))。

## 4. 结论:LangGraph 多 Agent 简历项目"最值得补齐的功能"排序清单

排序依据 = 多个独立来源(含两份真实面试实录)的交叉收敛度 × 来源可信度。按投入产出排序:

| 优先级 | 功能 | 面试官核验方式 | 证据来源(可信度) |
|---|---|---|---|
| **P0-1** | **上线 + 可试的 Live Demo**;项目叙事=真实问题(直接对话 ChatGPT/豆包解决不了的场景) | "你这个项目为什么必须存在?""让我试试" | Joye(高)、matthewraynor(中)、aitechconnect(中高) |
| **P0-2** | **评估体系**:评测集(20–100 条,含正常/噪声/故障注入)、指标口径(完成率/P95/工具失败率)、基线对比、可回归 | "90.6% 怎么算的?测试集什么分布?怎么回归?" | Joye(高)、F5(高)、aitechconnect(中高)、LangChain 数据(高)、JavaGuide(高)、HTMLPAGE(中) |
| **P0-3** | **可观测性**:每次 run 留 trace(prompt/模型版本/工具调用/耗时/状态),可回放,附一个真实 Badcase 复盘(现象→根因→修复→回归用例) | "线上出过什么问题,怎么定位修复?""trace 怎么逐节点解释?" | Joye"replay 真加分"(高)、aitechconnect"trace=不可伪造证据"(中高)、F5"讲不出事故=prototype"(高)、JavaGuide(高) |
| **P1-4** | **工具设计 + 稳定性**:tool schema/描述打磨、超时/重试/指数退避、幂等、降级、HITL 确认点、prompt injection 意识 | "一个工具 15% 超时,你的错误处理长什么样?""写操作超时=失败吗?" | F5(高,工具层是故障最大来源)、JavaGuide(高)、aitechconnect tool schema=High 信号、CSDN(中) |
| **P1-5** | **记忆系统设计决策**:写入选什么(事实/派生/偏好)、短期 vs 长期提升机制、矛盾处理、过期策略;**prefix-caching 友好布局**(稳定内容前置、异步低频更新) | "用户说今天想吃辣的,记不记?怎么分短长期?" | Joye 两份实录(高)、F5 memory tradeoffs(高) |
| **P1-6** | **上下文工程 + 成本控制**:前缀缓存、模型分层(小模型做通用/意图,大模型做推理/汇总)、上下文裁剪、Context/State/Memory 概念边界清晰 | "怎么控成本?""每个 agent 用不同模型吗?" | Joye(高)、F5(高)、HTMLPAGE(中)、CSDN(中) |
| **P2-7** | **MCP / Skills** 二选一做一个(小而有文档的 MCP server,或一个 SKILL.md + progressive disclosure) | "MCP 和 Skills 什么关系?" | aitechconnect(中高)、Joye(高,必考概念区分) |
| **P2-8** | **诚实的技术叙事定位**:区分 Workflow vs 真 Multi-Agent;讲清单 Agent→为何演进到多 Agent 的权衡,而不是"我就是用了" | "你的 agent 之间有通信吗?" | Joye(高)、JavaGuide(高)、Anthropic Building Effective Agents |

**明确不建议加/加前必想清楚(反模式清单)**:
- ⛔ Redis 存记忆 + TTL 过期删除(被面试官当场纠正:记忆是最珍贵资产,应归档不应删除)(Joye,高)
- ⛔ 无理由的微调(尤其培训班标配 Qwen3-8B——面试官原话"看到就 PTSD")(Joye,高)
- ⛔ 无通信的"多 Agent"(= Workflow 冒充 Multi-Agent,定义性陷阱)(Joye,高;Anthropic)
- ⛔ "多 Agent + GraphRAG + 微调 + 图数据库"全家桶但答不上任何一个"为什么"——**单个功能点的"能解释为什么"永远优先于功能数量**(Joye,高;Gunjan Sharma,中)
- ⛔ 虚构指标 / 把离线实验包装成生产数据 / 简历每句话能对应真实实现否则标注为地雷(Joye 第二场,高;JavaGuide,高)
- ⛔ 只堆功能不做 eval 和 trace(面试官视角的"toy",扣分主因)(CSDN,中;HTMLPAGE,中;F5,高)

**一句话**:对 LangGraph 多 Agent 简历项目,按「**上线 Demo → Eval → Trace/Badcase → 工具稳定性 → 记忆决策 → 成本/上下文**」补齐,且每补一项都能用一句"为什么不用 Y"讲清楚,否则删除该项。
