# 01 · 项目叙事与架构（面试开场 3 分钟版）

> 回答结构遵循「约束 + 选择 + 代价 + 证据」。所有数字见 [04-evidence-map.md](04-evidence-map.md)。

## 一句话

A 股投研报告生成平台：输入股票代码或话题 → LLM 规划检索方向 → 多源检索（本地研报 RAG / Tavily / 行情数据工具）→ 生成中文六段研报 → LLM 质量审查 → 不合格带意见回炉（回炉上限 `MAX_REVISIONS`，代码默认 3，`app/config.py:12`，部署环境可调）→ 支持多轮追问。

## 为什么不是"豆包直接就能解决"

约束：投研场景要的不是聊天，是**每一段落都有可追溯的数据来源**（`[来源: 同花顺官方API]` 标注是产品红线）+ 固定的合规结构（六章节）+ 可复用的本地研报库检索。通用 chatbot 不保证结构、不保证来源、不持久化调研上下文。代价：自建数据工具层（4 个工具 × 4 层降级链）和审查回路，复杂度显著高于包一层 prompt。证据：`backend/app/agents/prompts.py`（六章节 + 表格直接由 financial_data JSON 生成、不经 LLM 改写）；`backend/app/tools/akshare_tools.py`。

## 架构（LangGraph 状态机）

```
router（条件入口，非节点）
  ├── NEW_TOPIC → planner → researcher → search_agent ⇄ search_tools → data_collector → writer → reviewer
  │                                                                    └── FAIL → planner（≤ MAX_REVISIONS，默认 3）
  └── REFINE → refiner → END
```

- **为什么用状态机而不是链式调用**：审查回炉（reviewer FAIL → planner）和多轮追问（REFINE 分支）天然是图结构；chain 写法要手工 if/else 嵌套，图写法把回炉边显式化、可回放。
- **拓扑在模块导入时构建一次**（`app/graph/graph.py`）——代价是加节点必须重启服务；换来的是导入期校验拓扑正确性。
- **search_agent ⇄ search_tools 是 Function Calling 循环**：LLM 决定调什么工具、调几轮；用自研 ToolNode 而非 `langgraph.prebuilt`（版本兼容约束）。

## State Schema 设计（面试高频）

`AgentState`（`app/graph/state.py`，TypedDict）关键字段：
`query` / `plan` / `search_results` / `final_report` / `critique` / `review_status` / `revision_number` / `messages`（`add_messages` reducer 自动累加）/ `financial_data` / `conversation_summary` / `error_code` / `degraded`。

设计取舍：
- `search_results` 平铺不嵌套——writer 和 reviewer 都要全文读，嵌套只会逼人做拼接；
- `revision_number` 显式入 state 而不是用循环变量——它是回炉深度的可观测证据，SSE 事件和 trace 都要读它；
- `degraded` 布尔贯穿全链——mock 数据兜底时必须让下游知道，不许伪装成真实数据（`akshare_tools.py` 的 `degraded` 字段同理）。

## 模型分层（成本控制）

`app/utils/llm.py:48-58`：逐节点模型路由（`LLM_MODEL_{NODE}` 环境变量），fast(temp 0.7) 用于 router/planner/writer/refiner，smart(temp 0) 用于 grader/reviewer；主模型失败自动降级 fallback，额度类错误触发 5 分钟 TTL 熔断（`_EXHAUSTED_TTL=300`，`llm.py:64`）——TTL 内不再打主模型，避免每个节点都先吃一次 403。
