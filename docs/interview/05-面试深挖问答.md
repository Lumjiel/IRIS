# 05 · 面试深挖问答（预演 15 问）

> 回答结构统一「约束 + 选择 + 代价 + 证据」。带 ⚠ 的是答不好会翻车的点。

**Q1 为什么 LangGraph 而不是自己写 while 循环？**
约束：审查回炉 + REFINE 分支 + 并行搜索是图结构。选择：LangGraph 的显式拓扑、checkpoint 持久化、`add_messages` reducer。代价：框架版本耦合（因此自研 ToolNode 弃用 prebuilt）、加节点要重启（拓扑导入期构建，`graph.py`）。证据：`app/graph/graph.py`。

**Q2 State 里每个字段为什么存在？**（⚠ 灵魂题）
见 [01-项目叙事与架构.md](01-项目叙事与架构.md) State 节。最常追问：`revision_number` 为什么入 state——它是回炉深度，SSE 事件 / trace / 回炉上限（`MAX_REVISIONS`，默认 3）都依赖它，放循环变量等于不可观测。

**Q3 你的 Multi-Agent 真的是 Multi-Agent 吗？**
诚实回答：固定拓扑 + 条件边的 **Workflow**，不是自治 Multi-Agent——没有 agent 间自由通信，决策点在 router（LLM 分类）、search_agent（工具选择循环）、reviewer（通过/回炉）。这个定性本身就是加分点（参照真实面试复盘：固定 Router 分发 = Workflow 不是 Multi-Agent，承认比狡辩好）。

**Q4 记忆怎么设计的？短时 vs 长期怎么分？**（⚠）
三层：会话内 `messages`（reducer 累加）→ 跨轮 `conversation_summary`（增量更新，超 2000 字符触发 LLM 压缩，压缩失败降级句子截断，`memory.py:39-104`）→ 用户级长期记忆 store（watch_stock / fact / preference 三类，超限 `evict_oldest`，`memory_store.py:178`）。分类依据：行情关注是结构化的（带 stock_code 可直接喂工具），偏好是自由的文本，不能混存。代价：压缩调用有成本 + 失败路径要兜底。

**Q5 工具失败怎么办？**（⚠ 必问）
四层降级 + 重试封装（`_safe_request`：网络类错误重试 2 次、线性退避、参数类错误不重试）+ 超时（腾讯 3s、同花顾 `_timeout_s()`）+ fail-open（批量接口单股失败进 errors 不炸整体）+ 永不抛异常（失败返回结构化 JSON）。证据：`tests/test_fault_injection.py` 16 条故障注入（2026-11-10 绿）。

**Q6 mock 数据会不会污染研报？**
会——所以 mock 兜底必须带 `degraded=true` + 来源标注「内置模拟数据」，下游 writer 对 degraded 数据写 ⚠ 数据不足 而不是照抄。红线：不改 `[来源: ...]` 标注逻辑（`AGENTS.md`）。测试：`test_fallback_to_mock` 断言降级标记。

**Q7 怎么评测？90% 这种数字怎么来的？**
不给拍脑袋数字。可复现：299 tests / 69.37% 覆盖（`pytest --cov` 实测）；benchmark 五指标见 `docs/benchmark.md`，每轮标注环境与口径（数据层是否模拟、主备模型、token 估算方式）。被追问「测试集构成」时如实说：样本池 20 只已注册、5 只已实测，15 只待真实环境（`BLOCKED.md`）——不预填数字。

**Q8 一次生成延迟很高（中位 ~436s），为什么？优化了什么？**
定位：修订轮重跑完整研究管线是主因（v2 基线 600196 五轮 2508.8s）。优化：修订快速通道——`revision_number>=1` 时按审查意见定向补搜后直接重写，复用既有数据 → 600196 -78.3%、中位 -27.1%（v2.1，2026-11-08）。代价与残余问题：000333 反向 +362%，因为「修订=全文重写」仍在，下一杠杆是分章并行（Send API）。证据：`docs/benchmark.md`。

**Q9 成本怎么控制？**
三招：逐节点模型路由（router 用小模型，writer/reviewer 按需），额度熔断（403 后 TTL 5min 内不再打主模型，省掉每节点一次失败调用），token 观测（real/est 分开累计，`GET /api/usage`）。证据：`llm.py:48-87`。

**Q10 流式怎么实现的？**
ContextVar per-request 队列 + 生产者线程（同步 `llm.stream()`）+ async 消费者推 SSE + 15s 心跳。踩过的坑：LangGraph 并行分支拿不到 ContextVar（context 只沿 asyncio 任务继承链传播）→ 改 thread_id 显式注册表。证据：`streaming.py:47-63` + 注释。

**Q11 讲一次真实故障。**（⚠ 必问）
Case 1（`docs/badcase-review.md`）：主模型 403 后流式路径拿空报告。根因：降级策略只做了 invoke 路径，stream 路径吞异常静默失败。修复：对齐两路径 + 回归测试。反例也讲了：fallback 共享同一账号额度时修复不成立，但系统从「无解释空报告」变为「有降级标记的可观测状态」。教训：给一条路径加故障处理前先对齐兄弟路径。

**Q12 为什么 ChromaDB 不用 Milvus？**
约束：单机、2G 内存、研报量千级。选择：ChromaDB 嵌入式零运维，本地检索 <100ms。代价：不支持分布式/亿级；真到那规模迁移成本主要在 embedding 复用（接口已隔离在 `rag/engine.py`）。诚实回答「当前规模下选型正确，规模假设变了会重新评估」。

**Q13 RAG 的 reranker 为什么默认关？**
+400MB 内存（CrossEncoder），2G 机器装不下——资源约束 > 检索质量增益的边际。留了开关 `ENABLE_RERANKER`，接口层已隔离（`reranker.py` 95% 覆盖），机器升级即可开。

**Q14 上下文怎么裁剪？**
摘要压缩（超 2000 字符触发）+ 检索方向去重避让（planner 不重复搜，`build_conversation_context` 显式注入「已搜索方向」）+ 报告正文只取前 300 字入摘要。测试：`test_memory.py` 断言去重保序与截断。

**Q15 这个项目最薄弱的地方是什么？**（⚠ 主动交底加分）
1) 在线 eval 未建（只有离线 benchmark）；2) 修订=全文重写的成本未根除；3) 15 只样本 benchmark 数字待真实环境补。主动列出比被挖出来强。
